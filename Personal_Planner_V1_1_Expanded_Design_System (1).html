Planner Design System

A tactile, colorful interface system for the Personal Planner: part archival stationery, part weekly desk pad, part digital external brain. The supplied references are treated as the visual language—not as decoration pasted onto a generic productivity app.

Typography rules
  • Sentence case for user-authored content.
  • Uppercase + mono only for metadata, navigation labels and compact system language.
  • Never use all-caps for paragraphs.
  • Do not use handwritten or novelty fonts in core UI.
  • Use tight display tracking and comfortable body line-height.

19 / Mobile vs web product specification

The planner is one product with two deliberately different compositions. Mobile is optimized for thumb, glance and one-handed capture. Web is optimized for overview, comparison, planning and spatial manipulation. Do not simply shrink the desktop UI.

Core rule: same data, same behavior, different information density. Never change the meaning of an object between mobile and web just to make it fit. Change its presentation, navigation, density and interaction method.
Mobile~360–430px
Navigation
Bottom navigation. Calendar is the primary entry. Search and Settings live behind utility controls.
Density
One primary task per screen region. Prefer vertical stacks. Avoid side-by-side panels unless they are tiny controls.
Capture
Bottom sheet / full-height sheet. Keyboard opens automatically. Save returns to the current context.
Week
Seven-day vertical list. Each day shows a compact preview; tap to open the Day screen.
Month
Compact calendar grid. Show dates and tiny indicators only; never cram task titles into cells.
Cards
Full-width stacked objects. One card = one conceptual group. Progressive disclosure is preferred to shrinking text.
Tasks
Checkbox + title + optional metadata. Secondary actions appear in the task detail sheet, not inline.
Gestures
Tap first. Long-press/swipe is optional and must never be required for core actions.
Touch
Minimum 44×44px interactive target; 48px preferred for primary controls.
Web / desktop≥ 981px
Navigation
Persistent left sidebar. Calendar, Looking Back and Goals remain one click away. Search and Settings are utility actions.
Density
Use horizontal space for comparison. Two- and three-column compositions are allowed where they improve scanning.
Capture
Centered modal or anchored popover. Keyboard-first interaction is supported; Escape closes temporary surfaces.
Week
Seven-column planning board. Drag tasks between days. Empty day space can create a task with the date prefilled.
Month
Seven-column calendar grid with compact previews and +N disclosure. More horizontal context is visible.
Cards
Cards may sit beside one another in grids. Maintain minimum readable widths; never create a dense dashboard wall.
Tasks
Inline actions may appear on hover/focus. Detail can use a side panel or modal for richer editing.
Manipulation
Drag-and-drop is available for calendar planning, but every drag action must have a click/tap alternative.
Input
Mouse, keyboard and pointer. Visible focus states are required. Keyboard shortcuts are optional accelerators, never requirements.

20 / Accessibility

Accessibility is a component requirement, not a final QA pass.

REQUIRED
  • 44px minimum interactive targets.
  • Visible keyboard focus.
  • Semantic controls.
  • Accessible names for icon-only controls.
  • Color is never the only status signal.
  • Reduced-motion support.
  • Readable contrast even on pastel modules.
AVOID
  • Hover-only functionality.
  • Tiny calendar targets.
  • Pastel text on pastel backgrounds.
  • Animation needed to understand completion.
  • Icons without labels where meaning is ambiguous.
